# @atelier/db — Postgres migration notes

## Connection string

The admin app reads `DATABASE_URL` from the environment. Format:

```
postgresql://<user>:<password>@<host>:<port>/<database>[?sslmode=require]
```

Examples:

| Environment       | Value                                                                    |
| ----------------- | ------------------------------------------------------------------------ |
| Local dev         | `postgresql://postgres:postgres@localhost:5432/atelier_dev`              |
| Cloud SQL (direct)| `postgresql://postgres:<password>@<public-ip>:5432/atelier?sslmode=require` |
| Cloud SQL (proxy) | `postgresql://postgres:<password>@127.0.0.1:5432/atelier` (via Auth Proxy) |

Cloud SQL Auth Proxy is recommended for production. See:
<https://cloud.google.com/sql/docs/postgres/connect-auth-proxy>

## Local dev — pick one

1. **Docker (simplest):**

   ```powershell
   docker run --name atelier-pg -d -p 5432:5432 `
     -e POSTGRES_PASSWORD=postgres `
     -e POSTGRES_DB=atelier_dev `
     postgres:16
   ```

2. **Native install:** Postgres 16 from <https://www.postgresql.org/download/>.
   Create database:

   ```sql
   CREATE DATABASE atelier_dev;
   ```

After either path, run migrations:

```bash
pnpm --filter @atelier/db migrate
```

## Tests

Tests use `@electric-sql/pglite` (in-process Postgres) via
`getTestDb()` — no external server, no setup. CI does not need a Postgres
service.

```ts
import { getTestDb } from "@atelier/db";

const db = await getTestDb();    // fresh schema, applied via drizzle/ SQL
await db.insert(leads).values({ … });
```

## Migrations

Generated by `drizzle-kit` into `packages/db/drizzle/`. To create a new one
after editing `src/schema.ts`:

```bash
pnpm --filter @atelier/db generate
```

To apply to a real database (uses `DATABASE_URL`):

```bash
pnpm --filter @atelier/db migrate
```

The admin process also runs `runMigrations` on boot
(see `apps/admin/instrumentation.ts`), so the explicit migrate step is only
needed for one-off Cloud SQL bootstraps.

## Backup

The legacy SQLite `scripts/cron/backup-db.ts` is deferred (see file header).
For Cloud SQL, prefer the native automated backups + PITR; the in-app
schedule is commented out in `apps/admin/lib/cron.ts`.

## Concurrency

`claimNext` uses `SELECT … FOR UPDATE SKIP LOCKED` so multiple workers
sharing the same `pipeline_step` cannot claim the same job. This was a
hidden requirement under SQLite's single-writer model and is now explicit.
