# Cloudflare Pages Deploy Runbook

How to deploy any built Astro site (reference site or generated client site) to Cloudflare Pages. Confirmed working on Windows + PowerShell + wrangler 4.90.

## Authentication (one-time per machine)

Two paths — pick one:

### Option A — wrangler OAuth (recommended for spine, single laptop)

```powershell
npx wrangler login
```

Browser opens, sign in to Cloudflare, click "Allow" on the wrangler permissions screen. Credentials persist at `%USERPROFILE%\.wrangler\config\default.toml`. No env-var management needed.

Verify:
```powershell
npx wrangler whoami
```

Expected output includes `email thomas@aiwebatelier.com` and the account ID.

### Option B — API token in env (post-spine, multi-machine, CI)

1. Cloudflare dashboard → My Profile → API Tokens → Create Token → Custom token with permissions:
   - **Account → Cloudflare Pages → Edit**
   - **Account → Account Settings → Read**
   - **Zone → DNS → Edit** (scoped to `aiwebatelier.com` only — required for post-spine custom-domain attachment)
   - **Zone → Zone → Read**
2. Save the token to `.env` as `CLOUDFLARE_API_TOKEN` and the account ID as `CLOUDFLARE_ACCOUNT_ID`.
3. Token rotation every 90 days per `infra/cloudflare/token-rotation.md`.

Wrangler picks the token up automatically when both env vars are set.

## One-off manual deploy

For a reference site, the agency homepage, or any pre-built Astro project at `<sitePath>`:

```powershell
cd <sitePath>

# 1. Build (writes to ./dist)
pnpm exec astro build

# 2. Create the Pages project (first deploy only — idempotent on re-run)
npx wrangler pages project create <slug> --production-branch=main

# 3. Deploy on the production branch so the canonical *.pages.dev URL serves it.
#    --branch=main overrides the local git branch detection (this repo defaults
#    to 'master' from `git init`, but the project's production branch is 'main').
#    Without --branch=main, deploys land on https://master.<slug>.pages.dev
#    and the apex https://<slug>.pages.dev returns 404.
#    --commit-dirty=true allows deploying with uncommitted changes.
npx wrangler pages deploy ./dist --project-name=<slug> --branch=main --commit-dirty=true
```

The deploy prints two URLs:

- **Deployment-specific**: `https://<8-hex>.<slug>.pages.dev` — pinned to that exact build
- **Branch alias**: not printed when `--branch=main` matches the production branch
- **Apex (canonical)**: `https://<slug>.pages.dev` — always serves the latest production deployment, this is the one to email to leads

Verify the deploy is live:

```powershell
# expect 200 + brand text + correct robots meta
curl -sI https://<slug>.pages.dev | findstr "HTTP"
```

### Slug naming (per spec §7)

`<slug>` follows `kebab-case(business_name) + "-" + first-4-of-city + "-" + 4-char-nanoid`. Generated by `@atelier/shared`'s `generateSlug()` (Task 1.8). Cloudflare Pages constraints: ≤ 58 characters, lowercase a–z 0–9 and `-` only, must start with a letter, can't start/end with `-`.

The known-working live deploy:

| Site | Slug | URL |
|---|---|---|
| Bakery reference (Phase 0 C1) | `bakkerij-example-antw-ref1` | https://bakkerij-example-antw-ref1.pages.dev |

## Automated deploy (Task 4.3)

The generation pipeline's deployer worker will:

1. Take `dist/` from `/generated-sites/<slug>/`
2. Call Cloudflare REST API directly via `apps/admin/lib/cloudflare.ts` (lighter than spawning wrangler):
   - `POST /accounts/{account_id}/pages/projects` → create-or-reuse project named `<slug>`
   - `POST /accounts/{account_id}/pages/projects/{slug}/deployments` → direct upload of `dist/` contents
3. Throttle: 25-second sleep between consecutive `createPagesProject` calls (Cloudflare API allows ~3/min — see spec §11.4).
4. Capture the `*.pages.dev` URL into `generated_sites.cloudflare_preview_url`.
5. Run PageSpeed Insights against that URL → `generated_sites.lighthouse_scores`.

That worker code lives in Task 4.3 — this runbook documents the path it inherits.

## Rollback

Cloudflare Pages keeps every deployment. To roll back:

```powershell
# List deployments for the project
npx wrangler pages deployment list --project-name=<slug>

# Promote a specific older deployment to production
# (CLI doesn't have a single command for this — use the dashboard:
#  Pages → <project> → Deployments → ... → "Rollback to this deployment")
```

For programmatic rollback in Task 4.5 (edit-by-prompt version history), use the API:
`POST /accounts/{account_id}/pages/projects/{slug}/deployments/{deployment_id}/rollback`.

## Free tier ceiling

100 active Pages projects on the free tier. The `teardown-declined.ts` cron (Task 4.10) deletes projects for leads in `declined` status > 24h old to stay under the limit. Monitor active count via:

```powershell
npx wrangler pages project list --json | findstr name | find /c /v ""
```

When count > 50, plan the Pro upgrade ($20/mo, 1000 projects).

## Custom-domain attachment (post-spine)

When a client `accepts` an offer, attach a custom domain to their Pages project. This is a post-spine spec — code path documented in Task 4.x of the next milestone, not implemented in spine.

Manual reference for now:
1. Cloudflare dashboard → Pages → `<slug>` → Custom domains → Add a custom domain
2. Add the client's domain (e.g. `bakkerijdedesemhoek.be`)
3. Cloudflare provisions an SSL cert automatically once DNS points to it
4. Re-deploy with `SITE_STATUS=accepted` so noindex meta is removed:
   ```powershell
   $env:SITE_STATUS="accepted"; pnpm exec astro build
   npx wrangler pages deploy ./dist --project-name=<slug> --branch=main
   ```
